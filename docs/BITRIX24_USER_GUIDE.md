# Руководство по использованию в Bitrix24

Документ предназначен для администратора портала, автора автоматизаций и бизнес-процессов.
Названия пунктов Bitrix24 могут немного отличаться между облачной и коробочной редакциями.

## 1. Что потребуется

- права администратора для создания локального приложения;
- опубликованный HTTPS-адрес сервиса, например `https://automation.example.com`;
- успешно работающие `/health` и `/ready`;
- запущенный worker;
- client ID/secret, которые оператор сервера внесёт в `.env`.

> Не используйте `localhost`: серверы Bitrix24 должны видеть callback. Не вставляйте client
> secret, OAuth token или `EVENT_TOKEN` в роботов, вебхуки и переписку.

## 2. Создание локального приложения

1. В Bitrix24 откройте раздел разработчика: **Приложения → Разработчикам → Другое → Локальное
   приложение** (названия зависят от редакции).
2. Выберите серверное приложение с вариантом **использует только API** / без интерфейса.
3. Укажите начальный путь установки:

   ```text
   https://automation.example.com/api/bitrix/install
   ```

4. Если форма требует обработчик удаления, укажите:

   ```text
   https://automation.example.com/api/bitrix/uninstall
   ```

   При установке приложение также идемпотентно привязывает этот обработчик само.
5. Выберите права (scopes):
   - **Бизнес-процессы (`bizproc`)** — обязательно для регистрации и продолжения роботов;
   - **CRM (`crm`)** — обязательно для ожидания CRM-поля;
   - **Уведомления/IM (`im`)** — нужно для уведомления выбранных сотрудников;
   - **Списки (`lists`)** — нужно только для примеров и REST-вызовов списков;
   - добавьте scopes для любых других методов, которые планируете вызывать роботом
     «REST-запрос». Робот не обходит разрешения приложения и текущего портала.
6. Сохраните приложение. Передайте client ID и secret оператору сервера по защищённому каналу.
7. После внесения credentials и перезапуска API/worker установите или переустановите приложение.

Успешная установка регистрирует роботы **Короткая пауза**, **REST-запрос** и
**Ожидать заполнения поля CRM**. Если они не появились, см. раздел диагностики.

### Уже установленный портал

После обновления версии сервиса оператор может синхронизировать регистрации:

```bash
cd /opt/bitrix24-automation
sudo -u sinedis-bitrix .venv/bin/python -m app.bitrix.register_extensions
```

Команда обрабатывает активные порталы и не печатает tokens. Также можно переустановить локальное
приложение — installation callback обновляет определения без создания дублей.

## 3. Где найти роботы

### CRM-автоматизация

1. Откройте нужную CRM-сущность и раздел **Роботы и триггеры** / **Автоматизация**.
2. Выберите стадию, нажмите **Добавить робот**.
3. Найдите действие по имени в группе приложений и настройте его.
4. Сохраните и опубликуйте изменения.

### Бизнес-процесс

Откройте шаблон процесса в дизайнере, добавьте действие приложения в нужную ветку и используйте
его выходные значения в последующих действиях/условиях. Все три действия подписные: процесс
останавливается на этом шаге и продолжается после ответа worker.

Сначала проверяйте новую схему на тестовой стадии или тестовой сущности.

## 4. Робот «Короткая пауза»

### Параметры

| Поле в Bitrix24 | Обязательное | Описание |
|---|---:|---|
| Продолжительность, секунд | да | целое число; штатный диапазон 1–3600, может быть изменён сервером |
| Комментарий | нет | причина паузы, до 1000 символов |

### Пример

Чтобы дать внешней системе 20 секунд на обновление сделки:

1. добавьте **Короткая пауза** перед проверкой;
2. задайте `20` секунд;
3. укажите комментарий `Ожидание синхронизации`;
4. после робота добавьте условие, проверяющее обновлённое поле.

Доступные результаты: статус, UUID задания, плановое/фактическое время продолжения и
запрошенная/фактическая длительность. Пауза — не таймер реального времени: под нагрузкой
фактическое продолжение может быть позже на polling/сетевую задержку.

## 5. Робот «REST-запрос»

### Параметры

| Поле | Обязательное | Пример |
|---|---:|---|
| REST-метод | да | `lists.element.get` или `crm.item.get` |
| Параметры REST-запроса (JSON) | да | JSON **object**, до 100 000 символов |
| JSONPath | да | `$`, `$[0].ID`, `$[*].ID` |
| Уведомлять об ошибке | нет | один или несколько сотрудников |

Передаётся имя метода, а не URL. Не добавляйте `.json`, адрес портала или `auth`. Параметры
должны быть валидным JSON object: двойные кавычки, без комментариев и замыкающих запятых.

### Пример: найти элемент списка

```text
REST-метод: lists.element.get
JSONPath: $[0].ID
```

```json
{
  "IBLOCK_TYPE_ID": "lists",
  "IBLOCK_ID": 53,
  "FILTER": {
    "NAME": "{{Госномер транспортного средства}}"
  }
}
```

Подставьте ID списка и корректное выражение Bitrix24 вместо примера. JSONPath применяется не ко
всему HTTP-ответу, а непосредственно к его `result`:

- `$` — весь результат;
- `$[0].ID` — ID первого элемента;
- `$[*].ID` — ID всех элементов;
- `$.item.ufCrmField` — поле object-результата.

### Выходные значения

| Значение | Смысл |
|---|---|
| `status` | `completed` либо состояние ошибки |
| `job_id` | UUID для сопоставления с серверными логами |
| `result_text` | строковое представление выбранного значения |
| `result_json` | компактный JSON выбранного значения |
| `matches_count` | число совпадений JSONPath |
| `error_code`, `error_message` | безопасная диагностика; при успехе пусты |

Для ветвления сначала проверяйте `status`, затем `matches_count`. Ноль совпадений является
успехом: `result_text` пуст, `result_json` равен `null`.

> Не используйте универсальный робот для неидемпотентного изменения, если неизвестный исход
> неприемлем. При сетевом timeout метод мог выполниться, но ответ не был получен; результатом
> станет `rest_request_outcome_unknown`, и требуется ручная проверка по `job_id`.

## 6. Робот «Ожидать заполнения поля CRM»

### Параметры

| Поле | Обязательное | Описание |
|---|---:|---|
| ID типа CRM-сущности | да | числовой `entityTypeId`; для сделки обычно `2` |
| ID элемента | да | ID текущей сделки/лида/контакта/компании/смарт-процесса |
| Код поля | да | системный код, например `ufCrm...`; не отображаемое название |
| Интервал проверки, секунд | да | по умолчанию 30, максимум 86400 |
| Максимальное время ожидания, секунд | да | по умолчанию 86400, максимум 31536000 |
| Уведомлять об ошибке | нет | сотрудники для финальной ошибки или timeout |

Для динамических сущностей используйте фактический `entityTypeId` из Bitrix24. ID и код поля
лучше подставлять через поля текущего документа в дизайнере, а не вводить постоянным значением.

### Пример

Требуется ждать пользовательское поле сделки не более часа:

1. `ID типа CRM-сущности`: `2`;
2. `ID элемента`: выражение ID текущей сделки;
3. `Код поля`: фактический код вида `ufCrm...`;
4. `Интервал проверки`: `30`;
5. `Максимальное время ожидания`: `3600`;
6. выберите ответственного сотрудника для уведомления;
7. после робота создайте условие: `status = completed` — основная ветка,
   `status = timeout` — резервная ветка.

Пустыми считаются `null`, пустая или пробельная строка, пустой список и object. `0` и `false`
являются заполненными значениями. Timeout всегда продолжает процесс с
`error_code=field_wait_timeout`.

## 7. Рекомендуемая обработка результата

После каждого подписного действия добавьте условие:

1. успешный `status` — продолжить основной сценарий;
2. `timeout` — назначить ручную задачу или перейти в резервную стадию;
3. иной статус ошибки — записать `job_id`, `error_code`, `error_message` в комментарий/задачу и
   обратиться к оператору;
4. для REST-поиска отдельно обработать `matches_count = 0` и несколько совпадений.

Не показывайте конечному пользователю внутренние tokens или полный серверный лог. Для обращения
достаточно времени, портала, шаблона, сущности, названия робота и `job_id`.

## 8. Проверка после установки

1. Создайте тестовый процесс с паузой 5–10 секунд и действием после неё.
2. Запустите процесс и убедитесь, что он сначала ожидает, затем продолжается один раз.
3. Выполните безопасный read-only REST-метод и проверьте JSONPath/выходные значения.
4. Создайте тест ожидания поля, заполните его после старта и проверьте продолжение.
5. Повторите ожидание с коротким timeout и проверьте резервную ветку и уведомление.
6. Попросите оператора сопоставить `job_id` с логом и убедиться, что `/ready` отвечает 200.

## 9. Диагностика

| Симптом | Что проверить |
|---|---|
| Роботов нет в редакторе | приложение установлено после запуска сервиса; scope `bizproc`; установка вернула успех; выполнена синхронизация |
| Callback сразу отклонён | портал активен; приложение не пересоздано с другими credentials; системное время корректно |
| Процесс долго «выполняется» | worker активен; `/ready`; очередь и логи по `job_id`; доступность Bitrix24 |
| `rest_request_failed` | имя метода, JSON, scope и права; параметры метода по документации Bitrix24 |
| `matches_count=0` | JSONPath применяется к `result`; проверьте фильтр и регистр ключей |
| `field_wait_timeout` | правильны entity type/ID/код поля; значение реально непустое; timeout достаточен |
| Нет уведомления | выбран получатель; есть scope `im`; уведомление не заменяет основной результат |
| `portal_authentication_failed` | переустановить приложение или исправить client credentials; оператор проверяет статус портала |
| `event_token_invalid_or_expired` | процесс слишком долго ждал или подписка была отменена; запустить новый тест |

При инциденте не запускайте один и тот же неидемпотентный REST-запрос вручную до выяснения
исхода. Сообщите оператору `job_id` и следуйте [операционному runbook](OPERATIONS.md).

## 10. Удаление приложения

Удалите локальное приложение стандартным способом Bitrix24. Callback деактивирует портал, но
история и зашифрованные tokens сохраняются для аудита. Уже ожидающие действия могут не
продолжиться после удаления. Согласованное физическое удаление данных выполняет оператор базы
по политике хранения организации.
